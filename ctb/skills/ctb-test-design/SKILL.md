# CTB Test Design

## 目标

在 testcase 数量和比赛时间有限的前提下，用尽可能少的 testcase 区分尽可能多的错误实现。

重点不是“覆盖了多少方法”，而是：**哪些规则最容易写错、错误是否可观察、什么最小 testcase 能把正确实现与错误实现区分开。**

## 输入边界

输入为已经准备好的参赛者公开工作区。

只允许读取题目/需求、设计文档、接口说明、测试 AW、testcase 模板及比赛允许资源。

**禁止读取** `hidden/`、mutant、reference implementation、answer、oracle、历史隐藏评测结果及其他评测侧内容。

若题目同时提供需求、设计和接口文档：

1. 先识别各文档约束范围，不默认某一份永远优先；
2. 冲突或歧义必须记录，不自行补业务事实；
3. testcase 只验证公开资料能够推出的外部行为。

## 工作流

### 1. 先建“可测规格模型”，不要立即写 testcase

提取关键规格点，并为每个规格点记录：

- 规则/条件/状态迁移；
- 边界、优先级、顺序、时序；
- 会变化的数据；
- 明确要求保持不变的数据；
- 结构化响应中的主数据、派生/汇总字段及其可验证关系；
- 可通过哪些 AW/返回值/查询接口观察；
- 最可能的错误实现形态。

如果某条规则无法通过公开 AW 观察，不要为了覆盖率编造断言；标记为不可直接验证，并寻找等价外部现象。

### 2. 从“测试方法清单”转为“缺陷假设驱动”

对高风险规格点主动反推错误实现，例如：

- 边界偏移、条件遗漏/取反、`and/or` 错误；
- 分支优先级错误、默认分支错误；
- 状态更新过早/过晚、历史状态泄漏；
- 重复调用误触发、计时被错误刷新；
- A/B、主备、上下行、多实例只实现一侧；
- 目标字段正确但非目标字段被误修改；
- 对象 ID/主状态正确，但关键属性被替换或污染；
- 明细数据正确，但 `count/total/summary` 等派生结果与明细不一致；
- 非法输入产生部分副作用；
- 批量/时间推进与逐步执行语义不一致。

每个假设必须回答：**最小区分 testcase 是什么？需要观察什么？**

详细扫描方法见 `references/design-playbook.md`，只在对应规则出现时按需使用，不机械全展开。

### 3. 给测试点排序，而不是平均用力

优先级按以下顺序判断：

- `P0`：高概率错误 + 高区分度 + 可稳定观察；
- `P1`：重要规则或高风险状态组合，但区分度一般；
- `P2`：低风险重复验证、仅换数据、价值不明确。

首轮先完成 P0，再补 P1。没有新增区分价值的 P2 默认不写。

优先选择“一条轨迹同时区分多个相近错误实现”的 testcase，但不要把无关测试意图硬塞进同一条用例。

### 4. 对关键规则做最小覆盖矩阵

以下情况不能只抽一条代表 testcase：

- 多条件：关键条件逐个翻转，必要时做 MC/DC 类组合；
- 边界：真正有区分度的 `b-1 / b / b+1`；
- 状态机：进入、保持、退出、重复、非法/不可达转换；
- 对称对象：`关键操作 × 关键状态 × 对称对象`；
- 副作用：同时检查“应变化”和“应保持不变”；
- 结构化响应/集合：验证主数据与 `count/total/summary` 等派生字段自洽；判断“包含某对象”时，不只看数量或 ID，还检查公开规格要求的关键属性；
- 时序/计时：边界前、边界点、边界后，以及重复动作是否刷新计时；
- 非法输入：异常类型/返回值 + 状态原子性；
- 等价语义：如 `tick(n)` 与连续 `tick(1)` 的关系验证。

矩阵只展开高风险格子，不做全笛卡尔积。

### 5. 稳定设计后再映射 AW 和编码

- 不因为 AW 不方便就先删测试点；先找公开可观察的等价验证方式。
- testcase 名称体现测试意图，不使用 `test_1/test_2`。
- 断言只验证外部可观察行为，不依赖实现细节。
- 连续状态场景可以在一个 testcase 内完成；彼此无关的缺陷假设保持拆分。
- 相同 setup 下的多个相关断言可以合并，减少 testcase 成本。
- 对结构化结果优先写“关系断言”，避免只验证一个叶子字段而放过互相矛盾的响应。

### 6. 正确环境验证

运行全部 testcase，必须在正确环境通过。

PASS 只证明 testcase、AW 调用和期望值与公开规格一致，**不代表已经发现隐藏 Bug**。

失败时优先检查规格理解、前置状态、AW 语义和断言，不修改测试意图去迎合当前实现。

### 7. 提交前做一次“错误实现反推”

不要只问“还有哪条规格没测”，还要问：

> 如果当前全部 testcase 都通过，我还能写出哪些明显错误但仍能通过的实现？

重点检查：对象身份正确但内容错误、主数据正确但汇总错误、成功返回但状态未真实变化、失败返回但已经产生部分副作用。

优先补能区分这些实现的 testcase。若只是同类数据重复，不补。

## 训练反馈模式

若调用方提供上一轮反馈，只接受：

- testcase -> bug_id 命中关系；
- 已命中 bug 集合；
- 已尝试测试点；
- NEW / REPEAT / MISS 分类；
- 已提炼的通用测试经验。

Bug ID 只作为区分度反馈，不根据编号猜隐藏答案。

下一轮：

1. 保留已有效 testcase；
2. 找 `REPEAT/MISS` 背后的规格维度缺口；
3. 只新增新的状态、条件、对象、边界、顺序或可观察关系；
4. 不通过换数据堆 testcase。

## 结构化设计状态

除比赛要求的 testcase 文件外，维护 `.ctb/design.json`，供下一轮增量设计使用：

```json
{
  "constraints": {"max_testcases": null, "time_limit": null},
  "spec_points": [
    {"id": "S01", "rule": "...", "source": "...", "observables": ["..."], "risk": "high"}
  ],
  "test_points": [
    {"id": "T01", "spec_ids": ["S01"], "hypothesis": "...", "discriminator": "...", "priority": "P0", "status": "implemented", "testcase": "test_xxx"}
  ],
  "coverage_gaps": []
}
```

保持短小，只记录后续决策真正需要的信息，不写长推理过程。

## 输出

1. 修改题目要求的 testcase Python 文件，并保证正确环境全部 PASS；
2. 更新 `.ctb/design.json`；
3. 生成简短 `ctb_design_summary.md`，只包含：关键规格模型、P0/P1 测试点、主要缺陷假设、当前覆盖缺口。
