# CTB Test Design

## 输入

一个已经下载到本地的题目目录。

只允许读取参赛者可见内容：题目/设计文档、接口说明、测试 AW、已有 testcase 模板及公开资源。

**禁止读取任何 hidden、mutant、bug、reference implementation、answer、oracle、历史评测结果等评测侧内容。**

## 目标

不是追求 testcase 数量，而是用尽可能少的高区分度 testcase 暴露更多独立错误实现。

## 工作流

### 1. 建立规格模型

先读完整题目，不立即写代码。整理：

- 输入、输出和可观察行为
- 状态及状态迁移
- 条件、规则、优先级
- 边界与特殊值
- 前置条件和操作顺序
- 跨字段/跨步骤约束
- 未明确但可能影响实现的歧义点

后续测试必须能追溯到规格或明确的缺陷假设。

### 2. 建立测试因子

从规格提取测试因子，不机械做笛卡尔积。至少检查：

1. 等价类
2. 边界及边界两侧
3. 条件真假与 MC/DC 类组合
4. 状态迁移及非法迁移
5. 操作顺序、重复操作和幂等性
6. 多条件优先级/覆盖关系
7. 默认值、空值、非法值
8. 数据之间的关联约束
9. 历史状态对当前行为的影响
10. “仅、必须、除非、同时、之前、之后、最多、至少”等强约束词

### 3. 缺陷假设

对每条关键规则主动反推“实现最可能怎么写错”。至少考虑：

- `<` / `<=`、`>` / `>=` 边界偏移
- `and` / `or`、条件遗漏或条件取反
- 分支优先级错误
- 默认分支错误
- 状态未更新、更新过早/过晚
- 上一次状态泄漏
- 重复操作处理错误
- 枚举/映射值写错
- 一个字段正确但组合场景错误
- 对称场景只实现一侧
- 特殊值被普通逻辑吞掉

每个假设都问：**什么最小 testcase 能区分正确实现和这个错误实现？**

### 4. 多视角深挖

首轮设计完成后再做三次扫描：

- `规格扫描`：是否存在未覆盖的必须行为？
- `实现者扫描`：如果我是开发者，最可能在哪些地方写错？
- `反例扫描`：当前 testcase 全通过时，还有什么错误实现也可能全部通过？

只补新增方向，避免换数据重复验证同一逻辑。

### 5. 经验模式系统展开

历史经验不是“补一个同类 testcase”，而是一个**扫描规则**。命中以下模式时，先列一个很小的覆盖矩阵，再选有区分度的 testcase。

#### 重复/幂等

检查所有可能重复调用的关键操作：

- 第一次调用产生什么变化；
- 中间状态再次调用是否错误重置计时/状态；
- 已完成状态再次调用是否产生多余副作用。

不要只挑一个接口做重复调用测试。

#### 对称/镜像

存在 A/B、主备、上下行、两个方向、多个实例时，不只做“一条反向用例”。至少检查：

`关键操作 × 关键状态 × 对称对象`

优先覆盖带计时、状态迁移、清理/复位等容易硬编码的操作。

#### 副作用边界

凡规格描述“只修改 X”“其他保持不变”，测试必须同时断言：

- 应变化字段确实变化；
- 不应变化字段保持；
- 正向路径与中间状态路径至少各检查一次。

避免只断言最终主状态。

### 6. 映射 AW 并生成 testcase

测试设计稳定后再映射 AW 并编码。

原则：

- 不因为 AW 不方便就删除测试设计；先寻找组合 AW 或最小替代验证方式。
- testcase 名称体现测试意图，不使用 `test_1/test_2`。
- 一个 testcase 尽量验证一个清晰缺陷假设；连续状态场景除外。
- 断言验证外部可观察行为，不验证实现细节。
- 优先设计能区分多个相近错误实现的关键 testcase。

### 7. 本地正确环境验证

运行全部 testcase。PASS 只表示 testcase、AW 调用和期望值与正确环境一致，**不代表发现隐藏 Bug**。

失败时先修 testcase，不改变规格意图迎合运行结果。

### 8. 提交前自检

- 是否存在只有 happy path 的规则？
- 数值边界是否覆盖真正有区分度的 `b-1 / b / b+1`？
- 组合条件是否有单条件翻转？
- 状态机是否覆盖进入、退出、重复、非法和跨状态？
- 经验模式是否只是“抽样一条”，而没有覆盖关键操作/状态？
- 对称对象是否在计时、状态迁移、复位等关键动作上均有检查？
- 状态迁移是否同时验证“应变化”和“应保持不变”的数据？
- 是否存在明显错误实现仍能通过当前全部 testcase？

## 训练反馈

若调用方提供上一轮反馈，只接收：

- testcase -> bug_id 命中关系
- 已命中 bug 集合
- 已尝试测试点
- 未命中/重复命中的 testcase
- 历史练习提炼出的通用测试经验

不要根据 bug 编号猜答案。Bug ID 只用于判断哪些设计有区分度，以及下一轮应探索哪些规格 GAP。

## 输出

默认修改题目要求的 testcase Python 文件，并保证本地正确环境全部通过。

同时生成简短 `ctb_design_summary.md`：

- 关键规格模型
- 已覆盖测试点
- 主要缺陷假设
- 本轮新增探索方向
- 尚存疑点

保持简洁，不输出长篇推理过程。
