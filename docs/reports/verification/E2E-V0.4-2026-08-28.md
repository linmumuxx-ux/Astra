## 系统 E2E 运行边界

E2E 每次创建临时目录，并启动隔离的 Redis、Celery Worker/Beat、FastAPI、Vue 和可控 Agent 子进程。数据库、员工工作空间、执行记录和端口均不复用日常开发环境，结束后自动清理。

新增的正式询问场景验证：

1. 创建一名启用自动领取和自主执行的员工；
2. 检测其 Agent 与工作空间，环境进入“正常”；
3. 从配置中心把员工模型改为 `deepseek/deepseek-v4-flash` 并保存，确认值已持久化且环境为“正常”；
4. 再修改并保存基本信息，确认环境仍为“正常”；
5. 从页面创建并指定“先询问使用者，再打印答案”的任务；
6. Worker 自动领取并启动第一条 Run；
7. Agent 返回结构化具体问题，任务进入“等待人工”；
8. 页面展示问题原文，E2E 填入固定答案“自动化验收答案”；
9. 第二条 Run 沿用第一条 Run 的执行会话；
10. 任务自动完成，`AC-01` 为 `SATISFIED`；
11. 两条 Run 分别为 `BLOCKED` 和 `PASSED`，Token 与工具事件均有真实记录。

这条用例会在答案未传入恢复 Prompt 时让 Agent 替身直接失败，因此不仅验证页面状态，也验证人工答案确实回到了原执行会话。

## 已知部署边界

- Linux 远程执行仍需在目标主机验证 SSH、Agent、工作空间和模型网络；
- 当前现场没有公司 MySQL 与 Windows 主机，真实 MySQL 连接、PowerShell 启停和 Windows Celery 长时间运行需在公司镜像补充验收；
- Celery 上游不承诺 Windows 支持；Windows 启动器固定使用 `solo` 池，严格 SLA 时建议把调度运行时放在 Linux；
- 正式外部任务源需在对端接口可用后联调；
- 管理台不含登录/RBAC，正式部署必须置于可信内网或企业认证网关之后。
