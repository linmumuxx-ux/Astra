# Astra V0.3 需求说明书

## 1. 版本目标

Astra V0.3 对平台职责进一步收敛。

Astra 不负责任务执行过程的具体编排，不定义员工必须按照哪些步骤完成工作，也不规定员工必须使用哪些 Skill、Tool、脚本或验证方式。

Astra 只负责：

* 定义任务；
* 明确任务类型、分类和优先级；
* 指定或分配数字员工；
* 定义验收标准；
* 管理数字员工的工作环境；
* 观察员工工作状态；
* 记录员工工作进展；
* 处理人工介入；
* 保存任务结果；
* 统计 Token、Tool 等工作消耗。

任务真正如何完成，由数字员工自身的 OpenCode Agent 决定。

整体关系：

```text
任务创建
  ↓
明确任务目标和验收标准
  ↓
分配数字员工
  ↓
员工进入自己的工作空间
  ↓
OpenCode Agent 自主完成任务
  ↓
员工提交结果和验收情况
  ↓
Astra 保存结果、过程记录和工作消耗
```

---

# 2. 产品定位

Astra 是面向长期运行数字员工的任务管理和工作观察平台。

它不是：

* Coding Agent；
* Agent 工作流编排器；
* 测试脚本执行平台；
* Skill 管理平台；
* Tool 管理平台；
* 测试流程引擎。

Astra 主要回答以下问题：

```text
现在有哪些任务？
哪些任务最重要？
谁正在处理？
员工在哪里工作？
员工当前在做什么？
是否遇到阻塞？
任务最终是否完成？
验收标准是否满足？
本次工作消耗了多少模型和工具资源？
```

---

# 3. 核心原则

## 3.1 任务描述目标，不描述执行步骤

Astra 任务只定义：

```text
做什么
为什么做
谁来做
重要程度
做到什么程度算完成
```

不定义：

```text
先分析什么
后修改什么
调用什么 Skill
使用什么 Tool
执行什么命令
如何测试
失败以后如何修复
需要重试几次
```

这些属于数字员工自身的工作方式。

---

## 3.2 验收标准描述结果，不描述验证实现

Astra 保存：

```text
验收标准
```

例如：

```text
1. 登录接口当前 500 问题解决；
2. 原有登录功能保持正常；
3. 相关自动化测试通过；
4. 提供修改结果说明。
```

Astra 不要求配置：

```text
验证脚本
测试命令
真实验证脚本
Verifier
验证流程
```

员工自行决定如何证明验收标准已经满足。

---

## 3.3 工作空间属于员工

工程路径不再属于 Task。

每个数字员工在创建或配置时拥有自己的工作空间。

关系：

```text
DigitalEmployee
    │
    ├── OpenCode执行环境
    └── Workspace
```

任务分配给员工后：

```text
Task
 ↓
Employee
 ↓
Employee Workspace
 ↓
OpenCode
```

---

## 3.4 一个任务一个 OpenCode Session

员工工作空间可以长期复用。

OpenCode Session 必须按任务隔离：

```text
Employee
└── Workspace
    ├── Task A
    │   └── Session A
    └── Task B
        └── Session B
```

避免不同任务之间产生上下文污染。

---

## 3.5 Astra 观察工作，不规定工作方式

员工可以自主：

* 阅读代码；
* 搜索知识；
* 调用 Skill；
* 调用 Tool；
* 修改文件；
* 运行命令；
* 执行测试；
* 分析日志；
* 修复问题；
* 重试；
* 回退；
* 请求人工介入。

Astra 只观察其状态、进展和最终结果。

# 7. 任务类型

任务类型固定为：

```text
问题
需求
```

## 问题

用于处理：

* 缺陷；
* 故障；
* 异常；
* 现有功能不符合预期；
* 工程问题；
* 已有能力失效。

## 需求

用于处理：

* 新增功能；
* 能力增强；
* 工程改造；
* 体验优化；
* 新增工具；
* 代码重构。

V0.3 不增加更多任务类型。

# 10. 优先级划分原则

优先级依据两个维度判断：

## 重要性

表示任务对以下内容的影响程度：

* 业务运行；
* 版本交付；
* 核心能力；
* 用户使用；
* 关键质量目标；
* 重要项目或工作目标。

## 紧急性

表示：

* 是否需要立即处理；
* 是否存在明确时间窗口；
* 延迟处理是否会造成明显影响；
* 是否正在阻塞其他工作。

---

# 11. 优先级定义

| 优先级 | 重要性 | 紧急性 | 典型情况                           |
| --- | --- | --- | ------------------------------ |
| 很高  | 高   | 高   | 阻塞版本交付、核心功能不可用、严重影响业务运行，需要立即处理 |
| 高   | 高   | 中或低 | 重要功能、关键需求、影响范围较大，但可以按计划推进      |
| 中   | 中或低 | 中或高 | 普通问题、常规需求、有一定时效要求但整体影响有限       |
| 低   | 低   | 低   | 一般优化、体验改善、治理类工作、可延期事项          |

可以简化为：

```text
                    紧急性

                 高          低
            ┌──────────┬──────────┐
重要性  高  │   很高    │    高    │
            ├──────────┼──────────┤
        低  │    中     │    低    │
            └──────────┴──────────┘
```

创建任务时不要求额外填写：

```text
重要性
紧急性
```

只填写最终优先级。

页面可提供简短提示：

```text
很高：重要且紧急
高：重要但可以计划处理
中：有一定影响或时效要求
低：一般优化或可延期事项
```

# 13. 验收标准

验收标准用于定义：

> 什么情况下任务可以认为完成。

采用列表形式。

例如：

```text
验收标准

1. 当前500问题解决；
2. 原有登录功能保持正常；
3. 相关自动化测试通过；
4. 提供修改结果说明。
```

支持：

```text
添加一项
删除
调整顺序
```

---

# 14. 验收标准数据结构


```text

说明
证据
```

# 24. 工作空间

工作空间属于员工。

例如：

```text
Astra-01
└── /home/astra01/nr_test_system

Astra-02
└── /home/astra02/nr_test_system
```

员工可以连续在该工程中处理不同任务。

任务中不再配置工程路径。

---

# 25. 工作空间与任务关系

关系：

```text
Astra-01
    │
    └── Workspace
          │
          ├── TASK-001
          │      └── Session-001
          │
          ├── TASK-002
          │      └── Session-002
          │
          └── TASK-003
                 └── Session-003
```

Workspace 长期存在。

Session 按任务独立。

---

# 26. 员工并发

由于员工共享自己的长期工作空间，V0.3 默认：

```text
一个员工同时处理一个任务
```

即：

```text
max_concurrency = 1
```

V0.3 暂不考虑：

* Git Worktree；
* 一员工多工作空间；
* 一个员工同时多个 OpenCode Session 修改同一工程。

---


# 28. 工作策略

* 工作流配置。

# 36. 当前进展

员工工作过程中，可以持续向 Astra 上报：

```text
当前进展
```

例如：

```text

```

```text
已定位权限缓存问题，正在修改
```

```text
修改完成，正在执行相关检查
```

```text
正在整理最终处理结果
```

Astra 只展示这些信息。

不将其转换成固定 Phase。

---

# 37. 取消固定进度百分比

V0.3 默认不展示：

```text
68%
73%
91%
```

除非任务自身存在明确的可量化进度。

对于问题和需求任务，只展示：

```text
状态
当前进展
运行时长
```

避免产生没有可靠依据的百分比。

# 78. 首要验收场景

管理员创建任务：

```text
任务标题：
修复用户登录接口偶发500问题

任务类型：
问题

任务分类：
测试平台

优先级：
很高

任务描述：
用户登录接口在特定情况下偶发500，请定位并解决。

验收标准：
1. 当前500问题解决；
2. 原有登录能力正常；
3. 相关检查通过；
4. 提供修改结果说明。

执行员工：
Astra-01
```

Astra 完成任务定义。

之后：

```text
Astra-01
   ↓
进入自己的工作空间
   ↓
创建该任务独立OpenCode Session
   ↓
自主分析任务
   ↓
自主决定工作方式
   ↓
自主完成修改和检查
   ↓
根据验收标准确认结果
   ↓
提交任务结果
```

Astra 不介入中间工作方法。

# 80. V0.3 产品原则

后续开发统一遵守以下原则：

1. **Astra 定义任务，不定义任务执行步骤。**
2. **Astra 定义验收标准，不定义验证实现。**
3. **工作空间属于员工，不属于任务。**
4. **任务拥有独立 OpenCode Session。**
5. **员工如何完成任务，由员工自己的 Agent 决定。**
6. **Astra 不重复实现 OpenCode 已有的 Agent、Skill、Tool 能力。**
7. **任务状态保持简单，不将员工内部执行过程映射成固定流程。**
8. **工作进展由员工实际上报，不生成虚假百分比。**
9. **Token、Tool 属于工作观察数据，不直接作为员工优劣评分。**
10. **界面使用正常业务语言，减少英文标签和 AI Demo 式表达。**

Astra V0.3 最终定位收敛为：

> **面向长期数字员工的任务分配、工作观察、人工介入和结果管理平台。**

整体模型：

```text
                 Astra
                   │
          ┌────────┴────────┐
          │                 │
        任务              数字员工
          │                 │
   目标 + 验收标准       工作范围
          │             工作环境
          │             工作空间
          └────────┬────────┘
                   ↓
                OpenCode
                   ↓
              自主完成工作
                   ↓
        结果 + 验收情况 + 工作消耗
                   ↓
                 Astra
```
