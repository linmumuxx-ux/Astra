# Astra V0.4 需求说明书

## 1. 版本目标

Astra V0.4 在 V0.3“任务定义 + 数字员工管理 + OpenCode 自主执行”的基础上，重点补齐两项能力：

1. **持续运行与任务接续**

   * 数字员工持续在线；
   * 空闲后自动领取下一项任务；
   * 支持等待人工、挂起、恢复；
   * 支持 OpenCode、远程环境或 Astra 异常后的任务恢复；
   * 支持员工提交结果后的人工确认和退回继续；
   * 保证任务不会因系统重启或暂时异常而丢失。

2. **数字办公室与工作过程展示**

   * 首页增加“数字办公室”视图；
   * 每个数字员工拥有独立工位和状态；
   * 通过轻量动画体现工作中、空闲、等待人工、异常等状态；
   * 展示员工当前正在做什么，而不是只展示任务状态；
   * 工作过程采用“可读工作轨迹 + 详细操作 + 原始运行记录”分层展示。

V0.4 的核心目标：

> **让数字员工真正具备长期在线、连续工作、异常可恢复、过程可观察的运行能力。**

---

# 2. 产品边界保持不变

V0.4 不改变 V0.3 已确定的职责边界。

## Astra 负责

```text
任务
员工
任务分配
优先级
验收标准
员工状态
任务状态
运行状态
等待人工
挂起恢复
结果签收
工作轨迹
工作消耗
```

## OpenCode Agent 负责

```text
如何理解任务
如何制定工作计划
使用什么 Skill
调用什么 Tool
修改什么内容
如何验证
失败如何处理
是否需要重试
什么时候需要人工
如何满足验收标准
```

核心原则仍然是：

> **Astra 管工作，不指导员工如何工作。**

# 4. 自动连续领取任务

数字员工开启“自动领取任务”后，应长期保持工作循环。

员工完成一个任务后：

```text
任务完成
  ↓
员工状态变为空闲
  ↓
检查是否存在符合工作范围的任务
  ↓
有任务 → 自动领取
无任务 → 保持空闲
```

无需人工再次启动员工。

---

# 5. 任务领取顺序

V0.4 默认任务排序规则：

```text
1. 已明确指定给当前员工的任务

2. 自动分配任务按优先级：
   很高
   高
   中
   低

3. 同优先级：
   创建时间较早的优先
```

例如：

```text
TASK-001    中
TASK-002    很高
TASK-003    高
TASK-004    很高
```

领取顺序：

```text
TASK-002
TASK-004
TASK-003
TASK-001
```

V0.4 暂不提供复杂调度策略。

# 6. 员工状态

员工状态统一为：

```text
空闲
工作中
等待人工
已暂停
异常
离线
```

## 空闲

员工运行正常，目前没有正在处理的任务。

## 工作中

员工正在处理一项任务。

## 等待人工

当前任务需要人工参与，且员工当前不能继续正常工作。

## 已暂停

管理员主动暂停员工。

## 异常

员工运行环境或 OpenCode 执行发生异常，需要恢复或人工处理。

## 离线

员工运行实例不可用。

# 9. 等待人工

员工认为无法继续时可以主动请求人工介入。

典型场景：

* 缺少必要信息；
* 需求存在歧义；
* 权限不足；
* 外部环境异常；
* 需要业务决策；
* 高风险操作需要确认；
* 外部依赖不可用；
* 无法继续处理。

员工进入等待人工时必须提交：

```text
阻塞原因
已经完成的工作
当前进展
需要人工提供什么
```

---

# 10. 等待人工的两种方式

V0.4 区分：

## 10.1 占用等待

适用于：

* 当前 Workspace 存在无法安全切换的未完成修改；
* 当前工作状态不能安全挂起；
* 恢复必须依赖当前现场。

状态：

```text
Task      → 等待人工
Employee  → 等待人工
```

员工暂不领取其他任务。

---

## 10.2 挂起等待

员工判断当前任务可以安全停止并在后续恢复时：

```text
Task → 已挂起
Employee → 空闲
```

员工随后可以领取新的任务。

挂起任务需要保存：

```text
task_id
employee_id
opencode_session_id
当前进展
挂起原因
最后活动时间
必要的任务现场信息
```

人工补充信息后：

```text
已挂起
  ↓
恢复待处理
  ↓
重新进入员工任务队列
```

---

# 11. 任务恢复

任务恢复时应优先：

```text
恢复原 Workspace
       ↓
恢复原 OpenCode Session
       ↓
继续原任务
```

如果原 Session 已不可恢复：

```text
保留原任务记录
      ↓
建立新的 Session
      ↓
携带已有任务上下文继续处理
```

不应无条件从头重新执行任务。

---

# 12. OpenCode 异常恢复

以下情况不应立即将任务标记为“未完成”：

```text
OpenCode进程异常退出
OpenCode Session异常
SSH断开
Linux执行环境短暂失联
Astra服务重启
员工进程重启
```

任务首先进入：

```text
执行异常
```

保存：

```text
任务
员工
Session
最后进展
最后活动时间
工作环境
异常原因
已产生的Token
已产生的Tool记录
```

---

# 13. Astra 重启后的任务恢复

Astra 启动后需要检查：

```text
处理中
等待人工
已挂起
执行异常
```

等未终结任务。

检查内容包括：

```text
员工是否在线
OpenCode环境是否可用
原Session是否存在
任务最近进展
最后活动时间
```

根据实际情况：

```text
继续执行
保持挂起
保持等待人工
进入执行异常
```

不能因为 Astra 重启而直接重置任务。

---

# 14. 长时间无活动检测

任务处于：

```text
处理中
```

但长时间没有：

```text
工作进展
Tool活动
OpenCode活动
Heartbeat
```

时，应标记为：

```text
疑似异常
```

“疑似异常”属于运行提示，不新增主任务状态。

页面需要展示：

```text
最后活动时间
无活动持续时间
```

用户可以进一步：

```text
查看运行记录
继续
暂停
终止
```

---

# 15. 结果提交

数字员工认为任务满足验收标准后，提交：

```text
处理结果
验收结果
相关证据
```

Astra 不重新执行固定 Verifier。

---

# 16. 任务签收

任务增加：

```text
自动完成
需要确认
```

两种签收方式。

## 自动完成

员工提交结果后：

```text
处理中 → 已完成
```

适用于普通任务。

## 人工确认

员工提交结果后：

```text
处理中 → 待确认
```

由用户确认：

```text
确认完成
退回继续
```

---

# 17. 退回继续

人工认为任务未达到验收标准时：

```text
待确认
  ↓
退回继续
  ↓
处理中
```

退回必须填写：

```text
退回原因 / 补充意见
```

例如：

```text
登录正常，但异常场景回归覆盖不足，请补充后重新提交。
```

数字员工优先恢复原 OpenCode Session 继续工作。

不创建新的 Task。

---

# 18. 高优先级任务签收建议

V0.4 默认：

```text
很高 → 需要人工确认
高   → 可配置
中   → 自动完成
低   → 自动完成
```

用户创建任务时仍可以调整。

这只是默认规则，不改变任务优先级定义。

---

# 19. 工作过程展示目标

Astra 不展示完整 OpenCode 对话作为主要工作过程。

用户真正需要看到：

```text
员工现在在做什么
刚才做了什么关键事情
有没有卡住
修改和操作是否持续发生
距离上次活动多久
```

因此工作过程分为三层。

---

# 20. 第一层：工作轨迹

默认展示。

面向普通用户。

例如：

```text
09:12  领取任务

09:14  开始分析登录接口代码和异常日志

09:23  已定位问题与缓存刷新逻辑有关

09:31  完成相关修改

09:36  正在检查修改影响范围

09:42  发现一处关联问题，继续处理

09:51  相关检查通过

09:53  提交任务结果
```

工作轨迹不展示模型内部推理。

---

# 21. 工作进展由员工主动上报

员工 Agent 在出现有意义的工作变化时上报：

```text
当前进展
```

典型上报时机：

* 开始理解任务；
* 定位问题；
* 确认方案；
* 完成主要修改；
* 开始关键检查；
* 发现新的问题；
* 任务发生阻塞；
* 任务恢复；
* 验收完成；
* 提交结果。

不要求：

```text
固定时间上报
每调用一个Tool上报
每一步上报
固定Plan/Act/Verify阶段
```

---

# 22. 工作进展表达要求

工作进展应：

* 简短；
* 可读；
* 说明实际工作变化；
* 不暴露内部推理过程；
* 不输出冗长分析；
* 不使用 AI 流程术语。

推荐：

```text
已定位登录失败与权限缓存刷新有关，正在修改。
```

不推荐：

```text
Agent进入Reasoning Phase，调用Tool进行下一步Planning。
```

---

# 23. 第二层：详细操作

用户展开“详细操作”后可以看到实际工作行为。

例如：

```text
09:22  Read   src/login/service.py
09:24  Read   logs/error.log
09:28  Edit   src/login/service.py
09:32  Bash   pytest tests/login/
09:34  Bash   执行失败
09:35  Read   test-result.log
```

主要用于：

* 观察员工是否实际在工作；
* 排查异常；
* 判断资源消耗来源。

---

# 24. 第三层：原始运行记录

进一步进入运行记录时提供：

```text
OpenCode Session
原始日志
Tool详细信息
错误信息
Token变化
运行环境
```

这属于排障层。

正常工作观察不默认展开。

---

# 25. 工作事件来源

工作过程由两类信息构成：

```text
员工主动上报
+
OpenCode客观运行事件
```

## 员工主动上报

形成：

```text
工作轨迹
```

## 自动运行事件

形成：

```text
详细操作
Token统计
Tool统计
异常信息
```

Astra 不需要用另一个模型去总结完整 OpenCode 对话。

# 29. 数字办公室目标


# 30. 工位状态

## 工作中

表现：

* 显示器亮起；
* 有轻量数据流动画；
* 状态灯正常闪烁；
* 显示当前任务；
* 显示当前进展；
* 显示已工作时间。

例如：

```text
Astra-01

工作中

TASK-1028
修复登录接口异常

当前：
正在检查修改影响范围

已工作 38分钟
```

---

# 31. 空闲状态

表现：

* 显示器降低亮度；
* 工位保持在线状态；
* 可增加轻量咖啡杯等视觉元素；
* 显示：

```text
空闲
等待领取任务
```

不需要明显动画。

---

# 32. 等待人工

这是数字办公室最重要的提醒状态之一。

表现：

* 员工“举手”或类似提示动作；
* 橙色轻微呼吸状态；
* 显示等待原因；
* 显示等待时间。

例如：

```text
Astra-04

等待处理

缺少目标环境访问权限

已等待 17分钟
```

点击直接进入该任务的人工处理区域。

---

# 33. 执行异常

表现：

* 显示器进入异常状态；
* 红色状态灯慢闪；
* 显示简短错误原因；
* 避免强烈报警动画。

例如：

```text
Astra-03

执行异常

Linux工作环境连接中断

最近活动：3分钟前
```

---

# 34. 已暂停

表现：

* 工位整体降低亮度；
* 显示“已暂停”；
* 不进行工作动画。

---

# 35. 离线

表现：

* 工位灰化；
* 显示器关闭；
* 显示：

```text
离线
最后在线：18分钟前
```

---

# 36. 任务完成动画

员工完成任务时允许出现短暂轻量动画。

建议：

```text
约1秒
```

例如：

* 状态灯变为完成；
* 显示器出现简短 ✓；
* 完成后恢复空闲。

避免：

* 烟花；
* 大面积粒子；
* 游戏式奖励；
* 长时间动画。

---

# 37. 动画设计原则

Astra 的动画目标：

> **有生命感，但不像游戏。**

整体参考：

```text
专业工作台 70%
数字员工生命感 30%
```

保留：

* 轻微屏幕数据流；
* 状态呼吸；
* 工作中微动；
* 等待人工举手；
* 完成短动画；
* 状态切换动画。

避免：

* 高频闪烁；
* 大面积霓虹；
* 游戏 HUD；
* 强烈粒子效果；
* 影响信息阅读的持续动画。

---

# 38. 动画可关闭

用户应支持：

```text
减少动画
```

开启后：

* 停止持续动画；
* 保留颜色和图标状态；
* 不影响任何信息表达。

系统也应尊重浏览器：

```text
prefers-reduced-motion
```

# 60. V0.4 最终目标

V0.4 完成后，Astra 应能够呈现这样一种状态：

```text
办公室里有一批长期在线的数字员工

有人正在工作
有人刚完成任务准备接下一项
有人空闲
有人举手等待人工
有人出现运行异常

管理者无需打开OpenCode
就能知道：
谁在工作
在做什么
做到哪里
是否正常
需要不需要自己介入
结果是否可以签收
```

V0.4 的核心不是增加更多 Agent 功能，而是：

> **让数字员工持续可靠地工作，并让人能够像观察一个真实团队一样观察他们的工作状态和过程。**
