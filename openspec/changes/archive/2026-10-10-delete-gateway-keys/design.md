## Context

当前 DELETE 接口只吊销 Key，列表无删除入口。吊销摘要需要永久留在数据库，以便 Redis 丢失共享状态后重建。历史调用通过 Key ID 关联，无需删除。

## Goals / Non-Goals

提供持久的列表删除、即时阻断和明确确认；保留独立吊销操作。不提供恢复、批量删除或历史数据清理。

## Decisions

- 在现有 GatewayKey 行增加可空 `deleted_at`，作为是否删除的唯一事实源；历史行默认未删除。列表、单条管理读取和数据面配置加载排除已删除行，吊销摘要同步继续读取全部已吊销行。
- 删除复用吊销的共享阻断步骤，成功写入后在同一次短数据库更新中停用、补充吊销时间、标记删除并写 `key.delete` 审计。已吊销 Key 删除时保留原吊销时间；不在行锁中调用 Redis。
- 吊销使用 POST `/keys/{id}/revoke`，DELETE `/keys/{id}` 返回 204。前端分别调用，删除保留原确认交互、忙状态和失败通知，成功重新加载列表并复用既有分页修正。
- 物理删除会丢失重建阻断所需的摘要，仅前端隐藏则无法持久，均不采用。

## Risks / Trade-offs

- 新接口需要前后端同时升级；部署先执行 `alembic upgrade head`。外部旧 DELETE 调用需确认新的删除语义。
- Redis 不可用时删除返回 503，不写删除标记；共享阻断成功后数据库失败可能使 Key 先失效，重试可完成删除，优先保证失效安全。
- 回退代码可保留新列；若执行降级移除该列，已删除记录重新显示为已吊销，摘要与原吊销状态仍保留。
